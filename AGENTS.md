# Project guidance

- `bot.py` is a bidirectional GroupMe <-> Discord bridge. Each bridged GroupMe conversation maps to exactly one Discord text channel (`bridges` table, created with `/bridge add`). GroupMe messages arrive by polling (`GROUPME_MODE=poll`) or bot callbacks (`GROUPME_MODE=webhook`); both paths funnel through `Bot.process_groupme_message`.
- A GroupMe topic is a subgroup: detect it with `GET /groups/{id}/subgroups` (`id`, `parent_id`, `topic`). Topic bridges store `topic_id`/`topic_name` and `send_mode='user'`; they relay the parent's main chat plus that one topic into the channel, poll the topic every cycle (subgroups never fire bot callbacks), and post into it with `POST /groups/{topic_id}/messages`. They still need a bot on the parent group for main-chat callbacks; `poll_targets` polls the parent as a fallback when `bot_id` is empty.
- Discord -> GroupMe uses the group's GroupMe bot (`/bots/post`) for group bridges and the access token plus `image.groupme.com` uploads for topic bridges. `/bridge add` creates the group bot automatically (`groupme_create_bot`, `GROUPME_BOT_NAME`) and reuses an existing one when GroupMe answers "callback url ... already registered for group". Bot avatars must be `i.groupme.com` URLs (anything else is dropped), so they are re-hosted from the Discord avatar or `GROUPME_BOT_AVATAR_URL`; GroupMe has no bot update endpoint, so `/bridge set-avatar` deletes and recreates the bot. GroupMe -> Discord uses a per-channel webhook so sender names and avatars survive. Keep both idempotency guards: Discord skips `author.bot` and `webhook_id`, GroupMe skips `system`, non-`user` `sender_type`, missing `user_id`, and cached bot names (`BOT_NAMES`); topic posts are also recorded in `RECENT_OUTBOUND`/`message_links` so they never echo back.
- Discord text is rewritten before it reaches GroupMe: every message starts with `Nickname:` (picture-only bot posts include it too), user/role mentions become `@Name`, channels become `#name`, and emoji are stripped. Do not reintroduce Discord markup. Direction GroupMe -> Discord: messages from a topic are prefixed with `#<topic>:` via `groupme_content_for_discord`; main-chat messages are not prefixed.
- Images sent to GroupMe run through `compress_image` (Pillow): downscale to `IMAGE_MAX_DIMENSION`, re-encode as JPEG at `IMAGE_JPEG_QUALITY`, and lower quality until under `IMAGE_UPLOAD_LIMIT_BYTES`, then upload to `image.groupme.com` for both bot and topic bridges. Animated GIFs pass through untouched. GroupMe rejects non-`i.groupme.com` URLs (`invalid origin`), so never post a raw Discord CDN URL as `picture_url`; without an access token images are skipped and the message notes how many were dropped. Keep `read_body_limited` for downloads; `StreamReader.read(n)` truncates.
- Every `/bridge` command is administrator-only (`require_manager` plus the group's `default_permissions`); keep both checks in place when adding commands.
- GroupMe's API has no edit or delete endpoint, so message edits are not mirrored in either direction. Do not add code that pretends a GroupMe message can be mutated in place.
- `/bots/post` returns 404 for an unknown bot id; `recover_bot_id` repairs the bridge (find or create the group's bot, save the new id) and the relay retries once. `callback_url()` falls back to `NGROK_DOMAIN` so scripts that run outside the bot process can still create bots with a valid callback.
- Keep the single-file structure. Editing a bridge or its schema must remain safe for live state: `SCHEMA_VERSION` drops the tables on change, so bump it only with a migration plan.
- Read configuration from environment variables. Never commit credentials; update `.env.example` when configuration changes.
- Webhook mode can expose the aiohttp callback server through the `ngrok` SDK (`NGROK_ENABLED`, `NGROK_DOMAIN`, `NGROK_AUTHTOKEN`). The tunnel URL replaces `PUBLIC_BASE_URL` at startup and must stay in sync with what `/bridge add` prints.
- Preserve GroupMe request pacing/retries in `groupme_request` (429 + 5xx backoff, 304 means "no new messages").
- Dependencies belong in `requirements.txt`. Avoid adding a dependency for behavior the standard library already handles.
- Reusable scripts live in `utils/` (setup, bridge creation, bot maintenance, env sync, payload inspection) and checks in `tests/`. For Python edits run `python -m py_compile bot.py utils\*.py tests\*.py`, then `python tests\smoke.py` and `python tests\integration.py` (the integration test runs against a local fake GroupMe API on port 8731 and a temp database).
- Deployment lives in `deploy/`: `catbird-bot.service` runs `bot.py` from `/opt/catbirdBot` with `/opt/catbirdBot/.venv/bin/python` as the `catbird` user. Keep `WorkingDirectory` in sync with the paths in the README, and remember `deploy/` must stay tracked by git.
- `requirements.txt` pins ngrok by interpreter: `ngrok>=1.4,<1.5` below Python 3.12 and `ngrok>=1.7` at 3.12+. Both SDKs support the same calls used in `start_tunnel`; do not raise the floor without checking `requires_python` on PyPI.
